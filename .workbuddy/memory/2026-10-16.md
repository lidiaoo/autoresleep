## 唤醒原因通道调研（14:00）
- 用户点破关键前提：**他的网卡「只武装 magic-packet 也照样异常唤醒」（这个项目存在的理由本身）**，
  所以「wlan0 计数器命中 ⇒ 魔法包」不成立，我提的过滤器方案作废。
- 日志实证（journal.log）：10:27–12:31 多次 `collect kind=wifi-nic who=wakeup-event:wlan0@1s`
  发生在尚未开始发魔法包的时段 → 计数器命中 ≠ 魔法包；另有 11:33–11:42 多轮 `kind=unknown`（无任何归因）。
  13:32:19 那次是键盘唤醒（wake-by-input），计数器却报 `wlan0@40s` → 计数器语义松散，只能当「有无线活动」看。
- 关键发现（下一步要实测落地）：内核把所有无线驱动的唤醒原因**归一化为 `struct cfg80211_wowlan_wakeup`**，
  经 `ieee80211_report_wowlan_wakeup()` 上报；iwlwifi 的 mvm（CNVi 用的就是这个）与 dvm 都会从固件取回 reasons
  （`iwl_mvm_report_wakeup_reasons`）：MAGIC_PACKET→`magic_pkt`；MISSED_BEACON/DEAUTH→`disconnect`；
  GTK_REKEY_FAILURE→`gtk_rekey_failure`；RFKILL_DEASSERTED→`rfkill_release`；
  `IWL_WOWLAN_WAKEUP_BY_NON_WIRELESS`→报告为空（=根本不是无线唤醒）。**这才是「跨驱动统一」的正确落点**：
  不是解析驱动字符串，而是读内核结构体字段。来源：lore.kernel.org [RFC] iwlwifi: query and report WoWLAN wakeup reason + mvm/d3.c
- 用户态读取通道（三选一，待实测）：① `iw event`（项目 iwevent tap 已在跑，但行被 MOVE_PATTERNS 过滤掉）
  ② NetworkManager / wpa_supplicant 监听同一 nl80211 事件，journal 里可能有对应行 ③ `/sys/module/iwlwifi/parameters/debug`
  打开 D3 位 → dmesg 打印 wakeup reasons 十六进制。
- 若可读，收益有两块：a) 真魔法包唤醒 → 直接豁免（取代补按/证据波，解决今天的核心痛点）；
  b) 顺带修「resume 后 NM 重连被链路看门狗当成链路移动」的误回睡（wlan-events.log 13:50:47
  `disconnected (local request)` = NM 睡前主动断链，醒来必然重连 → 看门狗误判 NON_MAGIC_WLAN_LINK_MOVED）。
- 若三个通道全都读不到 → 系统内无法区分魔法包唤醒与网卡异常唤醒（包被固件消费是物理事实），如实告诉用户。
- 用户问「是否支持任意有线/无线驱动」——答（设计边界，写进文档时要保留）：
  **设备级**（谁唤醒的）= 通用：sysfs wakeup 计数器 / PME，任何网卡都适用（项目现在就用这层）；
  **原因级**（为什么唤醒）= 只有 cfg80211/mac80211 这一族（所有 in-tree 无线驱动）有统一结构体，
  且**是否上报取决于驱动实现**（Intel 报全，部分驱动不全或不报）；有线网卡**没有**原因级统一接口
  （ethtool 只能配 WOL 开关，唤醒原因多数不报，个别驱动打私有文本 → 退回字符串解析，不通用）。
  结论：原因级判别要做成「可插拔适配层 + 读不到就降级」，不能宣称全平台通用。
