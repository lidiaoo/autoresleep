### 结论
- **唤醒原因**：`evidence-last.json` → `chain=os, kind=wifi-nic, who=Killer(R) Wi-Fi 6 AX1650i 160MHz`，
  原始事件 `WakeSourceType=5, TargetState=4/EffectiveState=4, SleepTime=13:25:02Z, WakeTime=13:34:22Z`，
  `link=LINK_INTACT`（bssid 44:df:65:cd:00:00 / ssid meiyoumima_5G）。即**无线网卡造成的唤醒**，不是键鼠、不是魔法包。
- **为什么没回睡**：回睡窗口（`resleep_delay_seconds=10`）内 `window-input.json` 判定 `input=true`
  → `_may_latch_input("win32-window-tick")` 为真 → 写入 `session-cause.json{"cause":"input"}` →
  `decide()` 链 3 让**整个会话** skip（`who=input-this-session`），此后每次判定都是 `wake-by-input`。
- **这几乎肯定是误判**：21:34:24 时 `idle=603s`（说明 21:24:21 之后无人操作，与 OS 的网卡归因一致），
  但 `window-input.json` 的 `first_tick=129287953 → last_tick=129892562`（差 604.6s，换算约在 21:34:26）
  说明唤醒后 ~4 秒出现了一次输入 tick。这正是 Windows `GetLastInputInfo` 的
  **resume 后 HID 回放**被当成真实按键（`windowwatch.py` 与 `docs/resleep-window-plan.md` §10.2 已写明此限制）。
  出口开关：`resleep_break_on_input: false`（严格模式，忽略窗口内输入照睡）。

### 次要发现（可疑 Bug）
`_fast_path_judge()` 里 `sysinfo.suspend()`（Windows = `SetSuspendState`）**阻塞到唤醒才返回**，
导致之后的 `_mark_forced_sleep()` 写的是**恢复时刻**而不是睡眠时刻：
- `last-forced-sleep.txt = 1792071262.2616 129287953` → 1792071262.26 = 21:34:22.26（唤醒时刻），真实睡下是 21:25:07。
- `decisions.log` 21:34:22,276 因此多出一条 `SLEEP ... (listener fast path)` + `journal.log` 的
  `fast path: suspending via SetSuspendState(...)`，看起来像"唤醒瞬间又想睡"。
- 影响：`_finish()` 的 debounce 基线（`last_forced_sleep_at`）失真、`input_since_sleep` 的 tick 比对基准也失真。
  建议在 `suspend()` 之前（或由一个「睡下前」钩子）写标记。

## 实施：从根上修（两个修复都落地）

1. **新增 `input_settle_seconds`（默认 5s）= 把 Linux 的 `MOTION_SETTLE_S` 移植到 windowwatch**。
   `WindowState` 增 `settle_until` / `settled`；`observe()/sample()` 增 `settle_s` 参数：唤醒后
   `settle_s` 内的 tick 变化只进 `settled` 计数、不算人，**但仍折进 `last_tick`**（否则回放会在
   settle 结束后的下一秒被重新发现）。`cli._window_input()` 现在返回 3 元组
   `(input, source, settled)`；`Evidence.window_settled` 记录它；判定行打印
   `win=none@windows-window-tick(1-settled)`；`doctor` 打印该配置项。

   失败回滚（无 old 则删除、有则还原），时钟读不到降级成空 tick。`cmd_judge` 与 `_fast_path_judge` 都改走它。
